## 一、先记住面试官真正要判断的事

面试官通常不是在检查你会不会背 LangGraph，而是在判断四件事：

1. **是不是亲自做过：** 能不能画出数据流，指出自己改过的函数、接口、表或配置，并讲出一次失败。
2. **有没有工程判断：** 为什么选这个方案，为什么暂时不用另一个方案，代价是什么。
3. **能不能证明有效：** 测试集从哪里来，指标怎样定义，结果有没有对照和护栏。
4. **能不能迁移到业务：** 换模型、换数据、换并发规模、预算减少后，设计是否仍然成立。

因此，每个项目都要准备下面六个问题：

```text
为什么做？ → 不做会怎样？ → 为什么选这个方案？
→ 为什么不是替代方案？ → 怎么验证？ → 价值和局限是什么？
```

回答时优先使用“结论 → 机制 → 证据 → 边界”的顺序。先给结论让面试官抓住主线，再根据追问展开。

## 二、简历风险地图：哪些词会触发连环追问

| 简历关键词 | 面试官想确认什么 | 必须准备的证据 |
| --- | --- | --- |
| Agent Harness | 你是否理解模型之外的控制系统，而不是只会调 API | 状态、工具路由、权限、重试、终止条件、观测事件 |
| LangGraph / Deep Agents | 是否真的理解图状态和执行循环 | 节点输入输出、状态如何保存、异常如何回流 |
| Skills / 渐进式加载 | Skill 和 Tool 是否分得清 | Skill 文件结构、触发时机、加载方式、安全和版本 |
| MCP | 是否做过协议级工具接入 | initialize、tools/list、tools/call、鉴权、超时、错误归一化 |
| 子 Agent 委派 | 是否只是把多个模型调用称为多 Agent | 任务边界、上下文隔离、结果协议、失败处理 |
| 记忆 / Context Engineering | 是否知道什么该放上下文、什么不该放 | 会话状态、事实 / 情景 / 程序性记忆、压缩和预算 |
| RAG / 混合检索 | 是否能定位检索和生成的不同问题 | 切分、Embedding、召回、去重、重排、引用、指标定义 |
| 多模态 | 是否只有名词，没有真实数据流 | 图片 / 音频 / 文档输入，模型节点，输出和降级策略 |
| LLM-as-Judge / RAGAS | 是否把评分器分数当成真值 | 评分定义、校准、随机性、人工抽检、Judge 与 RAGAS 边界 |
| 36 条 / 8 条 / 5 条 | 数字是否能复核 | 数据来源、样本组成、报告位置、统计口径和局限 |
| Kafka 幂等 / 补偿 | 是否有真实后端可靠性经验 | 幂等键、状态机、重试边界、死信和补偿任务 |

**原则：**没有准备好机制和证据的词，不要在现场继续堆更大的词。可以把“我实现过”“我参与过”“我研究过”分开说，可信度反而更高。

## 三、三套必须背熟的项目讲法

### 1. 30 秒自我介绍

> 我是杨豪威，软件工程背景，目前做企业客户运营、AI 中台和智能客服相关的全栈开发。我的优势是能把 Agent 从模型调用落到业务系统：一方面做工作流、工具调用、MCP、Skills、RAG 和多模态输入输出，另一方面用 Django、Java、消息队列和前端把权限、状态、异步链路和异常处理接起来。最近我重点做的是 Agent Harness 和评测闭环，把推理、工具执行、上下文传递、流式展示和逐样本回归串成一条可追踪链路。

说完停住，不主动报十个框架。等面试官问项目，再进入下面的项目故事。

### 2. 主项目 30 秒版本

> 这个项目是面向企业知识问答、智能客服和业务自动化的多模态 Agent 平台。核心不是单次问答，而是用 Harness 把“模型决策、工具执行、结果回灌、状态管理和质量反馈”组织起来。系统支持工作流和循环任务、子应用、MCP、Skills、RAG、图像理解、语音转写与语音回复。我主要围绕工具调用链路、上下文和文件表单传递、流式事件归并，以及 CLI 加评测 API 的回归体系展开，最后用 36 条客服样本和边界复测定位具体退化案例。

**主动埋点：** Harness、Skills、文件表单传递、流式事件归并、36 条样本。每个埋点都要准备后面的答案。

### 3. 主项目 2 分钟版本

> **背景：** 企业客服既要回答知识问题，又要执行查询、表单、子流程和外部系统操作。只做一个聊天接口时，工具权限、上下文污染、流式分片和质量问题很难定位；只靠人工试聊，也无法稳定比较版本。
>
> **目标：** 我把系统拆成执行层和评测层。执行层负责图式工作流、模型决策、工具 / MCP 调用、Skills、文件和表单上下文、流式事件；评测层负责测试集版本、异步运行、检索指标、Judge 评分、基线差异和 Badcase 回流。
>
> **关键设计：** Harness 用状态和执行约束承接模型的不确定性：工具有 Schema、权限和错误回填，循环有递归上限，外部代码进入沙箱；Skill 以可加载的技能包组织多步流程，和原子 Tool 分开；上下文按会话、父子应用和工具调用组织，避免无关历史混入；RAG 把召回、上下文组装和生成分开看；流式结果按调用 ID / 索引合并，而不是按到达顺序盲拼。
>
> **验证：** 我开发了评测 CLI、API 和页面，支持 JSON / CSV 测试集、内容哈希版本、Celery 批量执行、规则指标和可选 Judge。当前客服样本 36 条，覆盖售前、售后、跨段和边界场景；一组 8 条边界复测中报告定位了 5 条评分退化案例。这个结果证明的是评测链路能发现差异，不把小样本 Judge 分数包装成线上准确率。
>
> **复盘：** 下一步会扩大真实线上样本和人工校准，补足运行配置快照、工具成功率、成本和延迟护栏，并把回归结果接入发布门禁。

## 四、Harness 连环拷打

### Q1：你说的 Agent Harness 到底是什么？和 LangGraph 有什么区别？

**推荐回答：**

> LangGraph 更像是编排状态图的运行框架；Harness 是围绕 Agent 运行建立的完整控制层。它不只负责“下一个节点是什么”，还要处理工具注册与权限、参数校验、执行超时、错误回填、循环上限、上下文预算、流式事件、日志和评测。我的理解是，模型负责提出行动建议，Harness 负责把行动放进一个可约束、可观察、可恢复的执行环境里。

**继续追问：为什么不能直接调模型 API？**

> 单次 API 足够做简单问答，但复杂任务会遇到工具结果过大、模型提前宣布完成、上下文膨胀、工具失败后无法恢复和权限边界不清。Harness 的价值是把这些“坏路径”设计成主路径：有状态、有上限、有错误协议、有外部验证。

**继续追问：你的 Harness 哪些是自己做的？**

> 我主要负责和实际业务链路相关的接入与改造：工具 / 子应用 / MCP 的调用链路、参数和权限边界、文件与表单上下文透传、流式工具事件归并，以及评测和回归接口。底层框架的通用能力是建立在已有运行时之上的，我的贡献重点是把它和业务场景、观测和质量闭环接起来。

### Q2：一次 Agent 请求从输入到结束，完整链路是什么？

按这张白板图讲：

```text
输入归一化
  → 加载会话 / 技能 / 可用工具
  → 模型决定回复或调用工具
  → Harness 校验权限和参数
  → 执行工具 / 子 Agent / MCP
  → 结果标准化并回灌状态
  → 继续推理或满足终止条件
  → 流式事件输出 + 记录运行轨迹
```

必须补充四个边界：

- 模型没有工具调用时可以直接结束，但仍要记录最终输出。
- 工具参数不合法时不能静默执行，应返回结构化错误，让模型修正或终止。
- 超时、限流、服务端错误要区分重试和不可重试错误。
- 递归 / 循环必须有上限，并由业务状态决定是否继续，而不是无限相信模型。

### Q3：为什么要用子 Agent？这是不是简单地多调几次模型？

> 子 Agent 的价值是隔离职责和上下文，而不是增加模型次数。主 Agent 做任务分解和汇总，子 Agent 只拿到完成子任务所需的输入、工具和权限，返回结构化结果。这样可以避免长工具轨迹污染主上下文，也能让检索、抽取、审核等任务有不同的提示和工具集。代价是调度、超时、结果合并和成本更复杂，所以简单任务仍然用单 Agent 或固定工作流。

面试官如果问“你有没有真正做多 Agent”，不要把普通节点都叫 Agent。可以说：

> 当前系统有主 Agent 调度子应用 / 业务子任务的形态；如果严格按独立角色、独立上下文和协作协议定义的多 Agent，我会把它作为进一步演进方向，而不是把每个工作流节点都夸成一个 Agent。

### Q4：工具失败怎么办？

用四步回答：

1. **分类：** 参数错误、权限错误、超时、限流、第三方 5xx、业务拒绝分别处理。
2. **恢复：** 参数错误回传可修正信息；限流指数退避；幂等操作可重试；不可重试错误直接终止或转人工。
3. **状态：** 工具调用必须有唯一调用 ID 和状态，避免重复执行产生副作用。
4. **观测：** 记录工具名、版本、耗时、输入摘要、结果状态和最终影响，敏感字段脱敏。

## 五、Skills、MCP 与上下文工程拷打

### Q5：Skill 和 Tool 到底有什么区别？

> Tool 是原子动作，例如查询订单、搜索知识、调用接口；Skill 是可复用的工作方法，描述什么时候使用哪些 Tool、顺序是什么、输入输出有什么约束。Tool 决定“能做什么”，Skill 组织“如何稳定完成一类任务”。Skill 不应该取代权限校验，真正的权限和副作用控制仍然在 Tool / Harness 层。

### Q6：你说“渐进式加载”，具体怎么做？

> 常驻上下文只放 Skill 的名称和简短描述，模型判断任务相关后再加载完整技能说明，必要时再读取模板或参考文件。这样 Skill 数量增加时，System Prompt 不会线性膨胀。加载时还要检查路径、大小、参数和来源，不能因为 Skill 是 Markdown 就默认可信。

**追问：Skill 如何防 Prompt Injection？**

> Skill 内容属于外部可变数据，必须和系统策略区分。加载前后做路径穿越、大小、文件类型和恶意指令检查；工具权限不由 Skill 自己提升；敏感操作仍需 Harness 的白名单和确认策略。对用户上传的 Skill，我会采用更严格的信任级别，并保留版本和审计记录。

**追问：Skill 自动生成后怎么保证不变差？**

> 不能只因为模型说“值得保存”就发布。至少要有固定回归集、版本 diff、失败样本和人工抽检；有确定性 verifier 的任务优先使用 verifier，没有时用 LLM Judge 加人工校准，并设置撤回和降级路径。当前项目已经有评测和 Badcase 基础，但自动 Skill 生成的完整质量闭环仍是后续工作，不能把研究设想说成已上线能力。

### Q7：MCP 和普通 Tool Calling 有什么区别？

> Tool Calling 是模型表达调用意图的消息机制；MCP 是把工具、资源和能力以统一协议暴露给不同客户端的连接标准。普通 Tool 可以在应用内直接注册，MCP 更适合跨进程、跨服务和跨客户端复用，但要额外处理连接生命周期、鉴权、超时、版本和不可信服务器风险。对业务系统来说，两者最终都要进入同一个 Harness 权限和错误治理层。

### Q8：记忆和上下文有什么区别？

> 上下文是当前一次推理可见的信息；记忆是跨轮次或跨会话保存、以后有机会重新取回的信息。事实记忆保存用户或业务事实，情景记忆保存过去发生的任务，程序性记忆 / Skill 保存“怎样做更有效”。不是所有对话都应该写入记忆，写入要有价值判断、来源、时间和可撤回机制。

**追问：长上下文怎么办？**

> 先分层：当前任务必须信息常驻，历史信息按需检索，大文件 offload 到外部存储；再做摘要或压缩，同时保留可回溯的 lineage。压缩不能替代权限和相关性过滤，摘要也要通过评测检查关键信息是否丢失。

## 六、RAG 与 Agentic RAG 拷打

### Q9：你的 RAG 链路具体怎么走？

```text
文档解析 / 清洗 → 分段 → Embedding 入库
→ dense + 全文候选召回 → 候选扩展与段落去重
→ 可选 Reranker → 上下文预算与引用定位
→ 生成 → 记录最终回答与证据
```

每一步准备一个失败例子：

- 切分过大：一个段落包含多个主题，召回相关性下降。
- 切分过小：上下文缺少前置条件，跨段流程回答不完整。
- 只有向量：专有名词、编号和精确字段检索容易漏召回。
- 只看候选池：候选命中不等于最终进入提示词，也不等于回答使用了证据。
- 只看 Recall：召回了正确文档但生成引用错，仍然是生成或证据组装问题。

### Q10：为什么要混合检索？为什么需要 Reranker？

> Dense retrieval 擅长语义相似，全文检索擅长专名、编号和精确词。混合召回先扩大候选覆盖，Reranker 再用更细粒度的相关性排序，最后才按上下文预算取结果。代价是延迟和成本增加，所以要用离线指标和线上延迟一起决定候选规模，不能只追求召回率。

### Q11：Recall、Hit Rate、MRR 分别是什么？

> Hit Rate 看一条样本的候选结果里有没有至少一个相关文档；Recall 看相关文档集合被命中了多少；MRR 看第一个相关结果排得有多靠前。当前评测按去重后的文档 ID 计算，属于文档级检索指标，不等价于段落完整性、答案准确率或线上解决率。

### Q12：Agentic RAG 和普通 RAG 有什么区别？

> 普通 RAG 通常是固定的“检索一次再生成”流水线；Agentic RAG 允许 Agent 根据问题和中间证据决定是否检索、如何拆分查询、是否二次检索、何时停止以及如何验证。它的收益是复杂任务更灵活，代价是调用次数、延迟、成本和行为方差增加，所以要设置搜索预算、停止条件和回归评测。

## 七、多模态与流式交互拷打

### Q13：你说多模态，具体支持什么？不是把图片转成文字吧？

> 我把多模态看成输入、理解、检索 / 执行和输出四段链路。图片可以进入视觉理解节点，文档进入解析和结构化节点，音频经过 ASR 转成可检索文本，最后根据场景输出文本或 TTS 音频。在客服和 IVR 中，关键不是“模型能看图”，而是要处理文件格式、大小、超时、转码、引用、降级和用户可感知的延迟。

**追问：图片如何进入 RAG？**

> 先区分两种路径：如果图片里的信息能稳定 OCR / 结构化，就把文本和版面字段纳入文本检索；如果图形、布局或视觉证据本身重要，就保留图片引用，在生成时把相关图像和文本一起提供给视觉模型。两种路径可以并行，但评测要分别验证 OCR 抽取、跨模态召回和最终回答。

### Q14：流式工具参数为什么会碎？你怎么处理？

> SSE 传输的是事件分片，模型的工具名称、调用 ID 和 arguments 可能分别出现在不同 chunk，甚至同一个模型只给 index、不稳定给 ID。接收端要先按调用 ID / index 建立累积槽位，再分别拼接名称和 JSON 参数，等收到结束标记后解析和执行；解析失败时保留原始片段和错误状态，不能把半截 JSON 当成合法参数。

### Q15：SSE 断线、重复和乱序怎么办？

> 事件要带会话 ID、调用 ID、序号或可恢复游标；前端按序号去重，服务端对副作用工具使用幂等键。断线后可以重连读取已确认事件，不能重复执行不可幂等操作。对用户展示的文本流和内部工具事件使用统一事件模型，避免前端靠字符串猜测状态。

## 八、Evaluation 评测拷打

### Q16：你的评测集从哪里来？36 条够吗？

> 36 条是当前用于验证流程的离线样本，不是可以代表全部线上分布的黄金 Benchmark。它由售前、售后、跨段和拒答边界组成，目的是覆盖几类已知问题并让评测链路跑通。正式上线前会从真实日志、转人工、差评和新功能变更中持续补样本，做正负样本平衡、难度分层和人工复核。评测集小的限制我会明确写进结论，而不是把小样本分数包装成生产效果。

### Q17：8 条复测定位 5 条退化，能说明什么？

> 能说明报告可以按同题对齐逐样本结果、计算维度差异并输出退化案例；不能单独说明系统准确率下降，也不能证明某个代码改动是因果原因，因为模型评分有随机性，且两次运行配置不一定完整冻结。下一步应重复运行、固定模型与提示、扩大样本、人工抽检，并区分检索不变而生成 / Judge 变化的情况。

### Q18：你说 RAGAS，报告里的 Faithfulness 是 RAGAS 吗？

> 两者要分开。评测代码可以接入 RAGAS 的 Faithfulness、Answer Relevancy 等指标；当前部分报告的 Faithfulness / Judge 分数来自自定义评分器或 LLM Judge，不能混称为 RAGAS 官方指标。面试中我会先说清评分器、输入上下文和聚合方法，再讨论分数，不把一个名称当成可信度证明。

### Q19：LLM-as-Judge 可靠吗？

> 它适合开放式质量维度，不适合替代所有确定性检查。我的组合顺序是：能用代码判断的先用代码，例如 JSON 合法、工具是否成功、文档 ID 是否命中；答案完整性、引用相关性等主观维度再用 Judge；关键样本用人工抽检校准。还要固定 rubric、temperature、模型版本，保存理由，监控评分漂移和与人工的一致性。

### Q20：评测结果怎么接发布？

> 当前系统已经能产生运行状态、基线差异和回归判定；要变成发布门禁，还需要把 CLI 非零退出码、阈值策略、人工审批、灰度观察和自动回滚接入发布流水线。我的回答会把“能发现回归”和“能自动阻止发布”分开，不把前者说成后者。

### Q21：如果离线指标涨了，线上没涨怎么办？

> 先检查分布漂移和指标相关性：线上问题类型、长度、语言、工具比例是否和离线集一致；再拆成检索命中、上下文使用、回答质量、延迟、转人工和成本几个维度。可能是离线集太干净、Judge 奖励了语言风格、线上工具失败或延迟导致用户中断。需要补真实 badcase，而不是继续调同一套离线分数。

## 九、SCRM 与后端工程拷打

### Q22：Kafka 消息重复怎么保证不重复触达？

> 我会用业务幂等键，例如事件 ID / 客户 ID / 动作类型组合，消费前检查处理记录或状态版本；状态推进采用条件更新，成功发送和状态回写要考虑重试边界。对可重试错误使用退避，对不可重试错误进入死信或补偿任务。不能只说“Kafka exactly once”，因为外部发送接口通常不具备真正的端到端 exactly once。

### Q23：企微回调验签和解密为什么重要？

> 验签确认请求来自可信平台，解密拿到业务载荷；两者都要在业务处理前完成，并校验时间戳、随机数和消息类型。失败请求直接拒绝并记录原因，不能让未验证数据进入客户关系或触达流程。密钥、用户隐私和消息内容要脱敏记录。

### Q24：如果 Agent 要调用客户触达工具，你怎么做权限控制？

> 采用最小权限：工具按应用、工作区、用户和动作范围授权；查询和写操作分级，副作用操作要求更严格的参数校验、幂等键和必要确认。模型只能提出调用，不能自行扩大权限。每次调用记录主体、工具、参数摘要、结果和审批 / 拒绝原因，支持审计和撤销。

## 十、常见“替代方案”与回答套路

| 面试官问题 | 推荐回答结构 |
| --- | --- |
| 为什么不用 Dify / Coze？ | 承认平台适合快速验证；说明当前场景需要更细的状态、权限、工具协议和评测控制；补充平台也可作为交付选择 |
| 为什么不用纯工作流？ | 固定流程更稳定、成本更低；开放问题和异常分支才交给 Agent；采用“确定性工作流 + 受约束 Agent”混合方案 |
| 为什么不用纯向量检索？ | 专名、编号和精确字段需要全文能力；混合检索用额外成本换召回覆盖，再由重排控制精度 |
| 为什么不用多 Agent？ | 多 Agent 增加通信、上下文和成本；任务边界明确时使用子 Agent，简单任务不强行拆分 |
| 为什么不用长上下文？ | 长上下文不是无限记忆；无关信息会增加成本和干扰，采用分层加载、检索、offload 和压缩 |
| 为什么不直接用更强模型？ | 更强模型能提高上限，但权限、可观测性、数据安全、延迟和成本仍需要 Harness；系统设计可以更换模型 |
| 为什么不用微调？ | 先判断是知识更新、流程控制还是模型能力不足；知识问题优先 RAG，行为约束先用 Tool / Skill / Prompt，稳定数据和明确目标后再考虑微调 |

通用句式：

> 不是说另一种方案不好，而是当前约束是【延迟 / 成本 / 权限 / 可解释性 / 数据变化】。所以我先选【方案】，它的代价是【代价】；如果规模或目标变成【条件】，我会切换到【备选方案】。

## 十一、六个可直接准备的真实故事

每个故事写在一张纸上，用“场景—任务—动作—结果—复盘”五栏，不要只背技术名词。

### 故事 A：工具参数分片与流式归并

- **场景：** 工具名称、调用 ID 和 JSON 参数分散在多个 SSE chunk，部分模型 ID 为空或只给 index。
- **任务：** 保证前端能展示完整调用，后端只执行一次合法参数。
- **动作：** 以调用 ID / index 建槽，分别累积名称和参数；结束标记后解析；失败保留原始片段和状态；副作用调用使用幂等控制。
- **结果：** 工具执行过程可追踪，避免半截 JSON 和错误关联。
- **复盘：** 还应补事件序号、断线恢复和更细的协议契约测试。

### 故事 B：父子应用文件与表单传递

- **场景：** 子应用需要使用父流程上传的文件或表单字段，直接读取会出现缺失或递归访问。
- **任务：** 在嵌套工作流中传递必要上下文，同时避免循环引用和无关数据膨胀。
- **动作：** 沿父工作流查找引用字段，限制访问范围，使用 visited 集合防循环；只透传白名单文件 / 字段。
- **结果：** 子任务能拿到需要的上下文，边界更可审计。
- **复盘：** 后续可以把上下文 schema、来源和版本显式化，便于跨节点调试。

### 故事 C：RAG 召回与生成分层排障

- **场景：** 客服答案错误，但不能确定是没有召回、上下文组装错误，还是模型生成问题。
- **任务：** 建立可定位的证据链。
- **动作：** 分别记录候选文档、去重结果、重排结果、最终提示词上下文和引用；用 Hit Rate / Recall / MRR 先看检索，再看 Judge / 人工抽检。
- **结果：** 能把“检索正确但回答错误”和“根本没召回”分开处理。
- **复盘：** 当前评测仍需扩大真实样本，避免把文档命中当成答案正确。

### 故事 D：8 条边界样本回归

- **场景：** 同一组边界问题重复运行后，报告出现答案正确性和 Faithfulness 下降。
- **任务：** 确认是检索变化、生成变化、评分器波动还是配置变化。
- **动作：** 对齐同题，查看逐样本答案、上下文、评分理由和配置差异；报告标记 5 条重点样本。
- **结果：** 评测链路发现了需要人工复核的退化案例。
- **复盘：** 8 条样本和 Judge 分数不能证明因果，要固定模型和提示、重复运行并扩大样本。

### 故事 E：多模态客服链路

- **场景：** 用户通过图片、语音或文档描述问题，客服还要查知识或执行工具。
- **任务：** 让不同输入进入统一任务编排，并保留原始文件和引用。
- **动作：** 文件校验与转码 → 图像理解 / ASR / 文档抽取 → 结构化上下文 → RAG 或工具 → 文本 / TTS 输出；设置大小、超时和降级。
- **结果：** 图像、语音和文本可以复用同一套工作流执行框架。
- **复盘：** 多模态质量要拆成识别、检索、生成和语音合成分别评估。

### 故事 F：Kafka 幂等与补偿

- **场景：** 企微回调可能重复，第三方发送可能超时但实际已成功。
- **任务：** 避免重复触达，同时保证最终状态可恢复。
- **动作：** 业务幂等键 + 状态机 + 条件更新；区分可重试和未知结果；未知结果进入查询 / 补偿任务，失败进入死信并告警。
- **结果：** 回调、消费、触达和结果回写链路可追踪。
- **复盘：** 继续补充对账、人工介入和跨服务 trace。

## 十二、面试回答技巧

### 技巧 1：主动埋点，但每个埋点都要有后手

好的埋点是“具体、可追问、你能讲深”。例如：

> 我重点做了流式工具调用的归并，难点是 arguments 可能跨 chunk；同时把评测从单次试聊变成了可对齐的逐样本回归。

这句话会引导面试官问两个你准备好的问题。不要埋“自研大模型”“百亿参数训练”这类无法证明的词。

### 技巧 2：每个回答只讲一个主结论

使用三层长度：

1. **15 秒：** 结论和取舍。
2. **60 秒：** 机制和一个例子。
3. **3 分钟：** 架构、失败、指标和复盘。

面试官打断时立即收束：

> 先说结论：这里我选择的是确定性工作流承接副作用，Agent 只负责判断和路由。具体状态流我可以再展开。

### 技巧 3：把“参与”说成贡献边界

不要说“整个系统都是我做的”。按下面方式说：

- **我负责：** 设计 / 编码 / 联调 / 修复 / 评测的具体模块。
- **我参与：** 接口定义、方案讨论、线上排障或某一条链路。
- **我研究：** 阅读源码、做概念验证、准备迁移方案，尚未作为生产能力交付。

### 技巧 4：所有数字准备“分母、时间、基线、方法”

面试官问任何百分比，都按这句话回答：

> 这个数字的分母是【样本 / 请求 / 文档】，统计时间是【时间】，基线是【版本 / 方法】，计算方式是【公式】；它的限制是【样本规模 / 评分器 / 分布】。

当前可以放心讲的数字是 36、8、5；原简历中的业务规模和效果数字，只有在你能拿出真实统计口径时再讲。

### 技巧 5：用“承认限制 + 给出下一步”应对质疑

> 这个结论目前只能说明离线样本上的现象，不能外推线上因果。我的下一步是固定模型和提示、扩大样本、增加人工双标，并把延迟、成本和转人工作为护栏。

这不是示弱，而是评测工程师应有的边界意识。

### 技巧 6：不要和面试官争论术语

如果对方说“这不算多 Agent”，回答：

> 如果按严格定义，需要独立角色、上下文和协作协议，那当前实现更准确地说是主 Agent 调度子应用 / 子任务。我愿意把它称为受约束的 Agent orchestration，而不是为了好听扩大定义。

## 十四、HR 与综合面问题

### Q：你为什么从全栈转 Agent？

> 我没有把全栈经验丢掉。Agent 真正落地时，难点正是模型之外的权限、状态、异步、观测、前端交互和业务系统集成。过去做 SCRM 和客户运营让我熟悉事件链路、幂等和第三方接口；现在把这些工程能力用到 Agent 的工具执行和质量闭环上，希望成为能把模型能力交付成产品的人。

### Q：你的优势和短板是什么？

> 优势是能跨模型、后端、前端和业务链路定位问题，不会只看最终回答；也会用评测和 badcase 把主观感觉变成可复查问题。短板是目前训练大模型权重、超大规模线上流量和严格人工标注体系的经验还不够，我在用数据构建、评测校准和工程化部署补齐，而不是把应用编排经验包装成模型训练经验。

### Q：为什么想来我们公司？

回答三段：

1. 公司真实业务与自己的 Agent / 客服 / 搜索 / 多模态方向有交集。
2. 自己能带来的具体能力：Harness、工具接入、RAG 排障、评测闭环和后端可靠性。
3. 想补的能力：真实流量评测、成本治理、模型训练或更复杂的多 Agent 协作。

不要只说“贵公司平台大、技术先进”。

## 十六、七天准备计划

### 第 1 天：简历逐词审计

- 每个名词写出“我做 / 我参与 / 我研究”。
- 删除无法解释的数据、框架和指标。
- 给每个关键词配一个代码入口、接口或故障案例。

### 第 2 天：画两张图

- Agent Harness：输入 → 状态 → 模型 → Tool / MCP → 回灌 → 终止 → 观测。
- RAG / Evaluation：数据 → 检索 → 上下文 → 生成 → 评分 → Badcase → 回归。

### 第 3 天：准备三个时长

- 自我介绍 30 秒。
- 主项目 2 分钟。
- 主项目深挖 10 分钟，至少包含一次失败和一次替代方案。

### 第 4 天：做一次白板追问

- Tool、Skill、MCP、子 Agent、Memory 各讲一遍。
- 手写 SSE 分片归并和 Kafka 幂等流程。

### 第 5 天：把评测讲实

- 说清 36、8、5 的来源和限制。
- 准备一个“离线涨、线上不涨”的分析方案。
- 准备一个 Judge 不可靠时的校准方案。

### 第 6 天：模拟连环炮

- 每个回答限时 60 秒。
- 被追问“为什么不是 X”时必须说出代价。
- 被质疑数字时必须说出分母、基线和局限。

### 第 7 天：收口与复盘

- 录音听 30 秒版本，删除口头禅和无关框架。
- 只保留 3 个最强故事：流式工具、评测回归、业务幂等。
- 准备两条反问，不在最后继续堆技术名词。
