从数据库中不难看出，我有一个已经做好的智能体：灯具知识问答助手。这个智能体，对应的知识库就是客服那个知识库，但是这个智能体的编排的节点感觉差点意思，我要你看下面的内容，你来规划下你会咋做，有哪些不太好做，做不了的，那些能做的。写在本文档的末尾吧。


RAG解决了“**知不知道**”的问题，命中率高意味着知识底座很扎实。但一个能真正在灯具店铺里工作的Agent，还需要解决“**会不会做**”和“**做得安不安全、稳不稳**”的问题。从RAG问答到可用的电商Agent，中间还缺好几个关键模块。

### 🧭 意图识别与任务路由：决定“该不该由RAG来答”
用户不会永远问“这款灯是什么色温”，他可能会说“我上周买的那个吸顶灯不亮了”。RAG面对这种请求是无力的，因为答案不在知识库里，而在订单系统中。你需要一个**前置的意图分类器**，把用户输入分流到不同的处理路径。

对于灯具店铺，典型的意图至少应覆盖：
- **知识查询**（参数、安装、色温选择、质保政策）→ 走你现有的RAG链路。
- **订单/物流查询**（“我的灯到哪了”“订单号xxx”）→ 走**业务工具调用**。
- **售后操作**（退货、换货、补发配件）→ 走**售后子流程**，通常需要多步确认。
- **转人工**（情绪激烈、复杂纠纷）→ 走**人工接管**。

如果缺少这一层，所有问题都涌向RAG，会出现两种后果：要么RAG对业务问题“硬答”，产生编造；要么智能体面对“帮我查一下订单”时束手无策。意图识别可以用轻量级分类模型（如微调的BERT）来实现，成本低且足够稳定。

### 🔧 业务工具调用：让Agent能“动手”，而不只是“动嘴”
这是灯具店铺Agent**最核心的增量模块**。RAG只能输出文本，但用户要的是“帮我看看订单状态”“能不能补发一个灯罩”。这需要Agent具备**Function Calling（工具调用）** 能力，去查询结构化的业务数据，或执行写操作。

对灯具店铺而言，必备的工具至少包括：
- **订单查询**：根据订单号或用户身份，返回商品、支付、状态信息。
- **物流追踪**：根据订单号查询物流节点，这是灯具这类大件商品的高频咨询。
- **售后操作**：提交退货/换货申请、补发配件工单。**写操作必须设计“先确认、后执行”的确认卡机制**，不能由Agent直接落库。
- **商品/SKU检索**：当知识库无法回答“还有没有黑色款”时，工具可以实时查询库存和规格。

工具调用的工程要点不在于“能调”，而在于**调得安全**：每个工具都要有严格的schema校验、权限控制（只能查本人订单），并对写操作设置人工确认闸门。多轮工具调用还需要设置步数上限，防止Agent陷入死循环。

### 🧠 会话状态与多轮记忆：灯具选购往往是“渐进式决策”
灯具咨询很少是一问一答。用户可能先说“卧室大概15平，想要暖光”，再问“那这款和刚才那款有什么区别”，最后说“就这个吧，有货吗”。如果Agent没有**会话状态管理**，第三轮对话就会失去前文的所有约束条件。

你需要维护一个结构化的会话状态，例如记录：**已提及的商品候选、房间类型与面积、色温/功率偏好、预算、当前处于“浏览/比较/决策”的哪个阶段**。每轮对话都先加载状态、更新状态，再进行推理。同时，要支持**指代消解**（用户说“那个灯”时，能关联到上文讨论的SKU）和**槽位补全**（用户说“查订单”，但没给订单号时，主动追问而非盲目调用工具）。

### 🛡️ 安全与护栏：电商场景的“必选项”，不是“加分项”
RAG测评很少覆盖的“边界拒答”，在灯具店铺里是刚需。至少需要三道护栏：
1. **知识边界拒答**：当RAG检索不到相关内容或置信度低于阈值时，Agent应明确表示“这个我不确定”，并引导转人工，而不是硬编一个答案。
2. **高风险操作确认**：退款、补发、修改地址等写操作，必须经过用户**明确确认**后才执行。部分系统还会对写操作引入**人工审核环节**。
3. **转人工兜底**：当检测到用户情绪激烈、连续多轮未解决问题、或触发敏感词时，平滑切换到人工客服，并传递完整的会话上下文。

### 📊 数据飞轮与可观测性：让Agent在真实店铺里“越用越准”
RAG命中率高，在静态测试集上成立，不代表上线后持续成立。你需要一套**线上反馈闭环**：把低置信度回答、用户负面反馈、转人工前的问题记录到“待优化池”，定期人工审核后反哺知识库或意图分类器。同时，对每个工具调用进行**审计落表**，记录“调了什么、参数是什么、返回了什么、用户是否确认”，这是排查事故和满足合规要求的基础。

### 💎 回到你的测评问题
上一轮提到的“知识库题目测知不知道，场景化任务测会不会做”，在灯具店铺的语境下可以具体化为：

- **RAG测评**：继续用你的知识库题目守住第一层。
- **场景化Agent测评**：新增“订单查询成功并正确转述物流状态”“缺货时主动推荐替代SKU”“用户要求退款时先确认再提交工单”“检索无结果时诚实拒答并转人工”等任务。评估指标相应地从Faithfulness**切换到** **Task Success Rate、Tool Call Accuracy、Confirmation Compliance**。

**RAG是Agent的“知识底座”，但灯具店铺真正要运转，还需要在它之上叠加：一个会分流的**路由器**、一套能安全查单和办售后的**工具层**、一个记得住“15平卧室暖光”的**状态机**，以及一道拦得住编造和误操作的**护栏**。这四层补上之后，你的智能体才从一个“很准的知识问答器”，变成一个“能接住灯具店日常咨询的服务角色”。\r\n\r\n## 针对“灯具知识问答助手”的落地规划（基于当前代码与数据库核对）

### 当前工作流结论

目前这个智能体是一个标准的知识库问答工作流，节点链路可以概括为：

`开始 → 知识库检索（客服知识库）→ 条件判断 → 命中直接回复 / 命中后 AI 对话 / 未命中兜底回复`

当前数据库中“客服”知识库有 3 份文档、205 个段落；工作流已经绑定这个知识库。现有工作流共有 7 个节点，已经具备知识检索、命中判断、AI 对话和直接回复能力。AI 对话节点的提示词已经要求使用客服口吻、不要提及知识库或文档来源，但还可以继续加强为更像真人客服的表达规范。

平台代码已经提供意图识别、参数提取、表单确认、工具调用、MCP、条件分支和变量节点。因此，工作流编排层具备扩展基础；当前缺少的是灯具店真实的订单、物流、库存和售后业务数据接口。

### 可以直接落地的部分

1. **先把知识问答改成稳定的真人客服口吻。**
   - 修改 AI 对话节点的 system/prompt：先给结论，再给操作步骤；使用“您”“这边”“可以帮您确认”等自然表达；避免“根据某某文档”“知识库显示”“检索结果表明”等内部话术。
   - 统一无答案回复，例如：“这边暂时无法确认，麻烦您提供灯具型号或订单信息，我再帮您核对；如果方便，也可以为您转人工处理。”
   - 增加禁止编造的约束：没有型号、订单状态、库存或政策依据时，不生成具体承诺，不猜价格、时效和结果。
   - 把安装、色温、功率、尺寸、质保等高频问题整理成客服知识库中的标准回答，减少模型自由发挥。

2. **增加轻量级意图路由。**
   在知识库检索前增加意图识别节点，至少分为：知识咨询、订单物流、售后申请、商品库存、投诉/转人工、其他。知识咨询继续进入 RAG；其他意图先进入对应的收集信息或转人工分支。该部分可以完全使用现有意图节点和条件节点完成。

3. **增加参数收集和确认卡。**
   对订单号、手机号后四位、商品型号、问题类型、照片等字段使用参数提取节点和表单节点收集。退货、换货、补发配件、修改地址等操作先展示确认卡，只有用户明确确认后才进入后续执行节点。

4. **完善评测集和线上质量指标。**
   保留现有 RAG 题目，同时新增场景题：无答案时诚实拒答、订单信息缺失时追问、售后操作先确认、情绪激烈时转人工、推荐替代 SKU 等。现有评测模块可以继续承载数据集、运行记录、结果和 badcase；需要在指标层补充任务成功率、意图分类准确率、工具调用准确率、确认合规率和转人工率。

5. **保留工作流版本和可回滚方案。**
   工作流修改后必须通过应用发布生成新的 ApplicationVersion，不能只改运行中的缓存或只改草稿。当前 Docker 的 `/opt/maxkb` 已映射到项目 `data` 目录，数据库数据具备持久化条件；发布前应导出工作流 JSON，便于回滚和重启后核验。

### 实现难度较高、需要额外工程的部分

1. **订单、物流、库存和售后工具。**
   平台有工具节点和 MCP 能力，但需要店铺提供真实 API、鉴权方式、字段定义、错误码和测试环境。工具必须限制只能查询当前用户可访问的订单，并对写操作做权限校验、参数校验、幂等处理和审计记录。没有这些接口时，不能靠工作流或提示词伪造业务结果。

2. **多轮会话状态。**
   当前工作流的 `chat_context` 主要是一次执行内的变量，聊天记录可以提供历史消息，但还没有针对“房间面积、色温偏好、候选 SKU、预算、当前任务阶段”的结构化状态模型。需要增加会话状态存储、更新规则、过期策略和指代消解逻辑，才能稳定支持“刚才那款”“就这个”“查一下它的物流”等表达。

3. **安全护栏和人工接管。**
   知识库低置信度拒答、敏感词检测、连续失败转人工可以先在工作流中实现；但真正的人工接管还需要客服系统或人工工作台承接，并定义会话转移、上下文传递、接管状态和恢复规则。退款、补发、改地址等写操作还需要人工审核或业务系统确认回调。

4. **线上数据飞轮。**
   当前已经记录检索候选、上下文、回答、耗时、token、反馈和 badcase 候选，但 `human_handoff` 等字段还需要由真实流程回填。后续要增加低置信度识别、负反馈聚类、工具调用审计、人工复核以及知识库回流流程，才能形成稳定的数据闭环。

### 当前不能单独完成或不应直接承诺的部分

- 不能在没有店铺业务 API 和授权的情况下查询真实订单、物流、库存，或执行退款、换货、补发和地址修改。
- 不能只通过改 prompt 保证模型永不编造；必须结合检索阈值、结构化工具返回、字段校验、确认闸门和审计。
- 不能把“转人工”做成一句提示语就视为完成，必须有真实的人工接待入口和状态回传。
- 不能把当前静态 RAG 测评分数直接等同于电商 Agent 的业务成功率；场景任务、工具结果和确认行为需要单独采集和评估。
- 不能仅修改草稿数据库记录来保证线上生效；必须发布新版本，并在 Docker 重启后核验应用版本和工作流内容。

### 推荐实施顺序

**第一阶段：客服表达和知识质量。** 先优化 AI 对话节点、无答案分支和知识库内容，补充真人客服场景题，验证回答是否自然、准确、不过度承诺。

**第二阶段：意图路由和信息收集。** 增加意图识别、参数提取、表单确认和转人工分支，但暂时只做信息收集，不执行真实业务写操作。

**第三阶段：接入只读业务工具。** 优先接订单查询、物流追踪和 SKU 检索；完成权限、超时、错误提示和工具调用审计后再上线。

**第四阶段：受控售后操作。** 接入退换货、补发和地址修改，强制“信息收集 → 展示确认 → 用户明确确认 → 执行 → 返回结果”的流程，并配置人工审核和幂等保护。

**第五阶段：线上闭环。** 建立转人工工作台、质量指标看板、badcase 审核、知识库回流和版本回滚机制，再逐步扩大 Agent 的自动处理范围。

按照这个顺序，当前可以立即完成的是客服表达、RAG 分流、信息收集、确认卡和评测扩展；真正依赖外部系统的是订单/物流/库存/售后工具、人工接管和写操作闭环。
