# 面试问题解答

## 1. RAG 全链路为什么按这个顺序？

链路是：**文档分段 → embedding → pgvector/HNSW → 候选扩展 → paragraph_id 去重 → 全文加分 → Reranker → 上下文预算**。

1. **分段**先把文档变成语义完整、可引用的最小单元。分得过大，主题不集中且占满上下文；分得过小，上下文断裂。
2. **Embedding**把问题和片段映射到同一向量空间，便于做语义近邻搜索。
3. **pgvector/HNSW**快速找到初始近邻。HNSW 是近似搜索，所以先取更多候选，给后续规则和重排留空间。
4. **候选扩展**补充命中段落附近、同文档相关段落或多路检索结果，解决“答案需要连续上下文”的问题；它解决的是覆盖率。
5. **paragraph_id 去重**避免同一段落重复占位，为更多独立证据留位置。
6. **全文加分**补偿关键词、实体、编号等精确匹配，向量相似度对数字和专有名词有时不可靠。
7. **Reranker**用更精确的交互模型重排较小候选集，解决相关内容排序问题，不能弥补候选集中根本没有答案。
8. **上下文预算**最后按 token 预算选择高分且互补的片段，避免检索噪声挤占生成空间。

候选扩展扩大覆盖面，Reranker 提高排序精度。上下文预算按模型窗口、输出预留和系统提示词开销计算，例如 32k 窗口预留 6k 输出和 2k 固定开销，检索约使用 24k token，并保留安全余量。

## 1.1 为什么不用独立的向量数据库？

并不是“不用向量数据库”：本项目使用 PostgreSQL 的 `pgvector` 扩展保存 embedding，并用 HNSW 索引做近似向量检索。这里没有额外部署 Milvus、Qdrant 等独立服务，主要是因为当前规模和查询特征下，数据库已经能满足需求：

1. **数据一致性更简单**：文档、段落、权限、租户和 embedding 在同一个事务和备份体系中，删除文档或重建索引时不会出现关系库与向量库状态不一致。
2. **过滤条件更自然**：检索通常同时按知识库、文档、权限和状态过滤，PostgreSQL 可以在 SQL 中完成 metadata 过滤、向量距离、全文检索和排序，减少跨服务拼接与网络往返。
3. **运维成本更低**：少维护一个集群、连接配置、监控、备份和数据同步链路；对几十万到数百万级向量，`pgvector + HNSW` 通常足够。
4. **检索链路已经是混合检索**：向量召回只是候选阶段，后面还要做邻段扩展、全文加分、去重和 Reranker。独立向量库不会自动解决这些排序和上下文问题。

独立向量数据库并非不能用。若向量规模、写入吞吐、并发查询或多模态索引显著增长，导致 PostgreSQL 的索引构建、查询延迟或资源隔离成为瓶颈，可以把向量检索拆到 Qdrant、Milvus 等服务。迁移前需要明确 metadata 过滤、权限同步、删除幂等、重建索引、备份恢复和一致性校验方案；否则只是增加系统复杂度，而不一定提升最终回答质量。

## 2. `hit_rate@5 = 80%` 怎么算？

固定测试集版本和标注规则。每个问题取最终 Top 5，只要至少一个结果的 `paragraph_id`（或所属 `document_id`）命中 gold 集，就记为 1：

```text
HitRate@5 = 命中问题数 / 有效问题总数 × 100%
```

例如 100 条有效问题中 80 条命中就是 80%。测试集应记录数量和构成（事实问答、跨段落、无答案等）；无答案问题另算拒答正确率。基线要保持数据集、Embedding、Top K 和阈值一致，比较“仅向量检索”和“向量+扩展+全文+Reranker”。

引用正确率 85% 需要人工标注：随机抽样并覆盖高频、点踩、无命中和长答案；两名标注者独立判断引用是否支持结论，分歧由第三人仲裁，同时报告样本数、置信区间和一致性（如 Cohen''s kappa）。

## 3. 40 万向量片段怎么来的？

这组数字应来自导入统计：1500 篇文档解析成约 6 万个逻辑段落，再切成约 40 万个向量片段，平均约 **6.7 个 chunk/段落**。最终以任务日志或数据库聚合为准，并记录失败、重复和过滤数量。

chunk 大小按 embedding 模型 token 上限和文档类型确定，采用目标长度加少量重叠（例如 400～800 token、10%～20% overlap），标题、列表和代码块优先保持完整；通过验证集比较 Recall@K、答案质量和 token 成本。HNSW 参数应写入检索快照并压测选择，常见起点是 `M=16`、`ef_construction=128`、`ef_search=64`，再按 Recall 与延迟曲线调节。

## 4. “召回到了但回答不对”如何定位？

先把一次请求固定成可回放的检索快照，至少记录 `query`、改写后的 query、过滤条件、候选段落及分数、每一步的 Top K、最终上下文、引用 ID、模型/Embedding/Reranker 版本、prompt 版本和 token 截断信息。然后从下游向上游逐层二分，判断证据在哪一步丢失或被误用：

1. **先确认问题和标注**：检查 query 改写是否改变了实体、数字或否定词，确认 gold 段落确实包含答案，并确认权限、知识库和文档状态过滤没有把正确证据排除。
2. **候选阶段**：gold 不在 `retrieval_candidates`，问题在分段、Embedding、向量召回参数、全文检索或过滤条件；分别跑“仅向量”“仅全文”和混合检索，比较 Recall/Hit@K，定位是哪一路没有召回。
3. **扩展、去重和重排阶段**：gold 在初始候选但不在扩展结果，检查邻段关系和 `document_id/paragraph_id` 映射；gold 被去重或被 Reranker 排出 Top K，检查去重键、分数归一化、Reranker 输入文本及排序方向。
4. **上下文组装阶段**：gold 在候选但不在 `final_contexts`，检查上下文预算、排序截断、重复段落占用和模型 token 计算；记录“截断前/截断后”的段落 ID，避免把组装丢失误判成模型问题。
5. **生成阶段**：最终上下文明确包含答案但回答仍错时，用完全相同的上下文和 prompt 脱离检索重跑模型。若仍错，检查指令冲突、历史消息、引用约束、温度和模型版本；若重跑正确，则重点检查 SSE 拼接、流式事件解析、上下文传递或前端展示。
6. **按失败特征归因**：长文档或跨段落失败通常看分段和邻段扩展；数字、编号、专有名词失败通常看全文加分、大小写和 tokenizer；只有流式结果错误则看 SSE 聚合和 finish 事件处理。

每次修复都保留原始快照，用同一版本测试集回归，并同时比较候选命中率、最终上下文命中率、引用正确率和端到端答案正确率，防止修复一个阶段后悄悄损害其他阶段。

## 5. Agent Runtime 和普通工作流的区别

普通工作流预先决定节点顺序，负责输入、条件、检索、重排和汇总。Agent Runtime 在受控工作流内运行，AI 节点根据状态动态选择已授权工具、循环调用并继续推理，不获得任意代码执行权限。

授权按应用、工作区和用户身份校验：API Key 有效且应用已发布；运行时携带 `workspace_id/application_id/chat_user_id`；工具列表只返回当前应用允许的工具，敏感工具还校验参数并可要求人工确认。沙箱工具使用受限后端和白名单目录，所有调用可审计。

## 6. MCP 与普通 Function Calling

Function Calling 是模型输出一次调用意图，协议和工具发现由应用自行约定。MCP 标准化 `initialize`、`tools/list`、`tools/call` 和工具 Schema，客户端与服务端可复用。

本项目把已发布 MaxKB 应用暴露为 `agent_<application_id>` 工具，Schema 是 object，必填 `message: string`；`tools/call` 创建子会话并流式收集回答。外部 MCP 工具初始化后转成 LangChain tools，保留名称、描述和 `inputSchema`，调用仍受应用权限边界约束。

## 7. Skills 是什么？和工具什么关系？

Skill 是可复用的任务说明、流程约束或领域知识，通常以目录或提示词资源注入 Agent；工具是有名称、参数 Schema 和副作用的可执行函数。Skill 告诉模型如何完成任务、何时用工具，工具负责实际执行。例如文档处理 Skill 规定先读取、再提取表格、最后引用来源，`read_file` 和 `write_file` 负责执行。Skill 不能绕过工具授权。

## 8. Deep Agents / LangGraph 怎么用？

LangGraph 用状态图表达运行时：状态包含消息、工具结果和变量；节点执行模型或工具，边按结果决定下一步；`MemorySaver` 以 `thread_id=chat_id` 做 checkpoint，支持流式运行和恢复。代码通过 `create_deep_agent` 注入 MCP/额外工具、沙箱 backend、`/skills` 和递归上限。

Deep Agents 用于动态规划、工具循环、文件操作和长任务状态管理。它不替代外层业务工作流，外层仍负责权限、输入、检索和最终响应。

## 9. SSE 工具事件跨 chunk 如何处理？

按 `index` 优先、工具 ID 兜底建立 fragment，保存 `id/name/arguments`。每个 chunk 合并 `tool_call_chunks`、`tool_calls`、`invalid_tool_calls` 和旧格式 `additional_kwargs.tool_calls`；占位 `{}` 后续出现真实 JSON 时用真实片段替换。遇到 `finish_reason == "tool_calls"` 或最后 chunk，解析 JSON、过滤运行时参数并生成 `tool_calls_info`。

完成标记必须幂等，已完成 fragment 不重复执行；缺少 ID、参数或 JSON 不完整时记录截断/失败。时序是：`delta(fragment) × N → finish(tool_calls) → assemble/validate → tool execute → tool result → model continue → final done`。

## 10. 父会话文件与表单如何透传？

父应用把文件列表和表单数据编码后传入。服务端只接受规定的文件字段并校验类型；表单先取父会话数据，再解析工具消息 JSON，按 `{**parent, **message}` 合并，使本次参数覆盖默认值。文件不塞进工具参数，而在工具描述中告知子应用当前附件，避免重复上传。

父会话用于保持用户身份、附件生命周期、权限和多轮上下文一致；子应用创建独立 chat 记录，便于隔离审计。字段白名单、类型/大小校验和合并快照保证边界清晰。

## 11. 评测闭环，以及 RAGAS 和 LLM-as-Judge 的区别

闭环是：**版本化数据集 → 采集真实回答和 SSE 完整性 → 保存候选与最终上下文 → 规则指标/人工抽样 → 可选 Judge → 与基线比较 → JSON/Markdown 报告 → badcase 回流**。每次运行保存应用、知识库、模型、prompt、Top K、阈值、Reranker 和评估器版本；回归阈值触发时阻断发布。

RAGAS 是面向 RAG 的指标与计算框架，常见有 context precision、context recall、faithfulness、answer relevancy。LLM-as-Judge 是让指定模型按 rubric 对答案、引用和拒答评分，适合复杂开放式质量，但有模型偏差和不稳定性，需要固定 judge 版本、温度和 JSON Schema，并用人工抽样校准。

检索指标包括 Recall/Hit@K、MRR、nDCG、context precision/recall；生成指标包括 answer correctness、faithfulness、citation relevance、拒答正确率和格式合规率；工程指标包括 SSE 截断率、延迟、token 与成本。报告必须同时给分母、样本数、基线和失败案例。
