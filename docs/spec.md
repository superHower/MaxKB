
## 第 0 步：先保留现有功能，隐藏独立入口

暂时不删除智能体测评代码，只在前端隐藏入口，避免影响现有 API 和历史数据。

但这一步只是产品入口调整，不能解决评测能力本身。

## 第 1 步：统一记录一次完整对话

先确保每次聊天都能稳定保存一条评测所需的记录：

```
问题
最终答案
检索到的段落
实际引用的段落
知识库和文档
模型、提示词、应用版本
响应时间
Token 和费用
用户反馈
是否转人工
```

这里最关键的是区分：

- 检索候选段落；
- 最终真正进入生成提示词的段落；
- 最终答案中实际引用的段落。

没有这部分数据，后面无法可靠评估引用准确性和忠实度。

## 第 2 步：从真实日志采样生成测评集

测评集不再主要靠人工编问题，而是从真实聊天记录采样。

采样规则可以包括：

- 高频问题；
- 点踩问题；
- 用户追问的问题；
- 没有命中知识的问题；
- 响应慢或消耗高的问题；
- 转人工的问题；
- 随机抽样的问题。

每条样本保存：

```
question
answer
contexts
application_version
knowledge_version
feedback
```

然后进入标注流程，而不是直接当作“标准答案”。

## 第 3 步：增加人工标注工作台

人工需要对样本标注：

- 答案是否正确；
- 引用是否相关；
- 是否应该回答；
- 无答案时是否正确拒答；
- 是否忠实于引用；
- 是否需要转人工；
- Badcase 原因。

Badcase 原因可以先固定为：

```
数据问题
检索问题
生成问题
提示词问题
模型问题
权限问题
用户问题
其他
```

这一阶段建立的人工标注，才是评估器和自动指标的依据。

## 第 4 步：加入自动评估器

在人工标注基础上，再加入 LLM Judge 或规则评估。

### 答案正确性

输入：

- 用户问题；
- 标准答案或人工标注；
- 智能体答案。

输出：

```
correct: true/false
score: 0~1
reason
```

### 引用相关性

判断引用是否真的支持问题和答案，而不是只看相似度。

### 无答案识别

重点评估两种情况：

- 知识库没有答案，智能体是否正确拒答；
- 知识库有答案，智能体是否错误地说“没有”。

### 忠实度

判断答案中的陈述是否都能被实际引用内容支持，降低幻觉。

自动评估结果必须保留理由，并允许人工改判，不能只保存一个分数。

## 第 5 步：建立离线回归评测

每次发生以下改动时，运行同一批固定样本：

- 修改提示词；
- 更换 LLM；
- 更换 Embedding；
- 调整切片；
- 调整 Top K 或相似度阈值；
- 增加或删除 Rerank；
- 修改工作流；
- 修改权限策略。

每次运行保存配置快照，比较：

```
答案正确性
引用相关性
无答案识别率
忠实度
命中率
延迟
Token
成本
```

离线评测的作用是：

> 修改上线前，先发现效果是否退化。

## 第 6 步：增加线上评测指标

线上指标来自真实用户行为和人工抽检。

第一批建议先做：

- 解决率；
- 一次解决率；
- 转人工率；
- 点赞率/点踩率；
- 引用准确率；
- 无答案率；
- 平均延迟；
- P95 延迟；
- 平均成本/次。

其中“解决率”不能完全靠模型猜，最好结合：

- 用户明确反馈；
- 是否继续追问；
- 是否转人工；
- 人工抽检；
- 会话是否在一次回答后结束。

## 第 7 步：灰度和 A/B

当日志和指标稳定后，再做线上实验：

- A/B 测试不同提示词；
- 灰度新模型；
- 灰度新的切片策略；
- 对比不同检索参数。

实验必须记录：

```
实验版本
用户或会话分组
命中的应用版本
命中的知识库版本
指标结果
```

不能只比较平均回答分数，还要看成本、延迟和转人工率。

## 第 8 步：Badcase 周期闭环

每周固定流程：

1. 自动收集低分、点踩、转人工、无答案、超时样本；
2. 人工抽检和归因；
3. 按数据、检索、生成、权限分类；
4. 统计各类问题占比；
5. 形成改进任务；
6. 改动后重新跑离线集；
7. 通过后再灰度上线。

这样才形成：

```
线上日志 → Badcase → 归因 → 修复 → 离线回归 → 灰度 → 线上观察
```

## 最合理的产品结构

最终不要把所有内容都叫“知识库命中测试”，而是拆成：

- **知识库检索测试**：单题、批量，关注召回；
- **智能体离线评测**：固定测试集，关注回答质量；
- **线上质量看板**：真实业务指标；
- **Badcase 工作台**：问题归因和闭环。

知识库可以作为测评集的主要来源，但不能替代智能体评测。因为“命中正确段落”与“最终回答正确”是两个不同环节。
最先应该做的不是 LLM Judge，而是**完整记录真实对话及其上下文**。数据链路建立后，后续的离线评测、线上指标、Badcase 闭环才有可靠基础。
