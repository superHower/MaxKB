# 灯具问答助手的记忆、Skills 与自进化能力评估

本文基于当前代码，并只读核对了数据库中灯具知识问答助手（应用 ID：`01a100ea-ca6a-7201-82d7-155928dc3fc6`）的草稿和最新发布版本 `01a160b8-f9bf-7030-9649-3b2991f239cb`。以下实际配置结论同时适用于这两份工作流；本次仅回答和设计方案，没有修改应用、记忆或 Skills 配置。

已阅读指定的 Hermes 文档。它是二次整理的学习材料；下面借鉴其闭环思路，没有进一步验证 Hermes 上游源码。材料中的 Star 数、固定 Token 预算、“零成本”、缓存策略和跨框架对比不能直接当作本系统的事实或效果承诺。用户消息里写 `[SYSTEM]` 也不会自动获得系统消息权限。

## 先给结论

当前系统已经有“对话历史 + 可选长期记忆 + Skills 工具 + 工作流版本 + 线上评测”的基础模块，但还没有形成 Hermes 意义上的自进化闭环。

当前灯具助手的实际状态是：

- 有会话历史：工作流开始节点能够获得历史聊天记录，AI 节点也配置了多轮对话数量。
- 有长期记忆代码，但灯具助手当前没有开启长期记忆；其工作流 `base-node` 中没有 `long_term_enable: true`。
- 有 Skills 能力，但灯具助手的 AI 回答节点当前 `skill_tool_ids` 为空，没有挂载任何 Skill。
- 有工作流节点编排：知识库检索、意图分流、条件判断、AI 回答和指定回复能在画布中体现；当前所谓“转人工”是固定回复提示，没有接入真实人工坐席。
- 有轨迹采集和质量评估基础：对话记录会保存节点详情，并生成 `EvaluationEvent`；评测模块支持测试集、运行记录、检索指标、Judge、样本审核和 Badcase。
- 没有自动从轨迹中提炼候选 Skill 或候选提示词，也没有候选版本的隔离验证、审批发布、自动回滚和继续训练闭环。

所以目前更准确的说法是：**这是一个具备记忆、Skills、评测和版本快照基础设施的工作流 Agent 平台，还不是 Hermes 那种“经验自动沉淀为技能并持续改进”的自进化 Agent。**

## 当前的记忆是怎么做的

### 会话记忆

每轮对话会保存到 `application_chat_record`，主要字段包括用户问题和回答、每个工作流节点的 `details`、模型调用的 token、耗时、回答片段、对话用户 ID、会话 ID、来源和反馈状态。

工作流开始节点会把历史记录整理为 `history_context`，AI Chat 节点根据 `dialogue_number` 读取最近的对话上下文。这属于**情景记忆/短期会话记忆**，作用是让当前会话连续对话，不等于 Agent 学会了新的方法。

### 长期记忆

长期记忆存储在 `application_long_term_memory`，以“应用 + chat_user_id”为维度保存一份文本记忆。

实现主要位于：

- `apps/application/models/application_chat.py`：`ApplicationLongTermMemory`；
- `apps/application/long_term_memory/__init__.py`：记忆提取、融合和调度；
- `apps/application/flow/step_node/start_node/impl/base_start_node.py`：读取长期记忆并暴露为开始节点变量 `memory`；
- `ui/src/workflow/nodes/base-node/index.vue`：长期记忆开关、模型和触发设置；
- `ui/src/workflow/nodes/start-node/index.vue`：把 `memory` 加入可引用的开始节点变量。

长期记忆提取由模型根据固定的 `long_term_prompt` 完成，提取偏好、背景、约定和目标四类信息，并支持按轮数、每日、每周、每月、间隔或 Cron 触发，再与已有记忆融合后保存。

这已经比“把所有聊天记录拼进 Prompt”更完整，但它仍然是**用户画像记忆**，不是 Hermes 的程序性 Skill。它记录的是“这个用户有什么偏好和背景”，没有记录“完成某类任务应该按照什么步骤执行”。

### 灯具助手当前是否真正使用了长期记忆

草稿和最新发布版本都没有配置使用长期记忆，数据库中该应用的长期记忆记录数也是 0。

读取当前工作流配置后，灯具助手的 `base-node.node_data` 没有开启长期记忆，开始节点虽然具备 `memory` 变量能力，但当前 AI 回答节点的 Prompt 也没有引用 `{{开始.memory}}`。因此当前线上回答不会因为这套长期记忆模块而改变。

如果要启用，需要同时完成：

1. 在基本信息节点打开长期记忆，配置触发方式和模型；
2. 在 AI 回答节点的系统提示词或用户提示词中有选择地引用 `{{开始.memory}}`。

还需要设置隐私边界：只记住用户明确表达且未来有复用价值的信息，不保存密码、身份证号、完整地址、支付信息等敏感数据。

当前按应用和用户 ID 存一段合并文本，没有独立的事实来源、置信度、修订历史和到期时间，也没有强制的总长度上限。用户身份必须稳定才能跨会话复用；并发更新还需要处理覆盖问题。代码在关闭长期记忆后存在清理已有记录的逻辑，不能把关闭开关当成“暂停提取但永久保留”。知识库 RAG 解决业务事实，会话历史解决上下文，用户记忆解决偏好，三者应分别管理。

## 当前有没有 Skills

有 Skills 功能，但当前灯具助手没有配置 Skills。

平台中的 Skill 是一种特殊的 Tool：`Tool.tool_type` 支持 `SKILL`，内容以文件保存，应用或 AI Chat 节点通过 `skill_tool_ids` 选择，运行时把已授权的 Skill 文件挂载到工具执行环境。相关代码包括 `apps/tools/models/tool.py`、`apps/tools/serializers/tool.py`、`apps/application/flow/step_node/ai_chat_step_node/impl/base_chat_node.py` 和 `ui/src/workflow/nodes/ai-chat-node/index.vue`。

当前灯具助手的 AI Chat 节点配置为 `skill_tool_ids: []`，实际没有加载任何 Skill。平台也没有 Hermes 那种自动创建或自动更新 Skill 的审查 Agent；目前 Skill 需要人工创建、上传、编辑，再在节点中选择。

这里已经有可复用的运行底座：`apps/application/flow/tools.py` 解压 Skill ZIP 到临时目录，检查 `..` 和以 `/` 开头的路径，通过 `create_deep_agent(skills=["/skills"])` 接入 Deep Agents 的技能发现/加载，并使用 `SandboxShellBackend`。具体索引和渐进加载行为取决于依赖实现，不能一概说平台完全没有按需加载或路径防护；基础路径检查也不等于完整的内容和权限审核。

但运行时的 `MemorySaver` 每次调用新建，临时目录在结束或异常时清理，文件修改没有自动写回持久化的 Tool/File。因此“模型在临时目录改了 Skill”不代表它已经学会并发布了新技能。你给全局 Codex 安装的设计 Skill 只供开发工具使用，也不会自动成为这个客服智能体的 Skill。

## 在工作流节点中能不能体现

能体现，但目前体现的是“能力配置”，不是“自进化过程”。

| 能力 | 工作流中的体现 | 当前灯具助手状态 |
|---|---|---|
| 会话历史 | 开始节点的 `history_context`、AI Chat 节点的 `dialogue_number` | 已有 |
| 长期记忆 | 基本信息节点的长期记忆开关；开始节点的 `memory` 变量 | 未开启，Prompt 也未引用 |
| 知识检索 | 知识库检索节点和检索结果变量 | 已有 |
| Skills | AI Chat 节点的 Skills 选择区和 `skill_tool_ids` | 为空 |
| 工具调用 | AI Chat 节点的工具/MCP/应用选择 | 当前主要使用工作流节点和知识库 |
| 人工接管 | 意图分流后的指定回复 | 只有引导话术，未接坐席系统 |
| 结果输出 | AI Chat 或指定回复节点标记为结果节点 | 已有 |

灯具助手当前的编排已经包含“意图分流 → 知识库检索 → 条件判断 → AI 客服回答/兜底回复”，而且 AI 回答提示词已经明确要求使用真人客服口吻、禁止提及知识库和文档。这是**人工设计的策略**，不是 Agent 根据历史轨迹自动总结出来的策略。

订单、售后、库存和转人工分支目前主要也是固定回复，不能将其描述为已经查询订单、校验库存或完成转接。后续画布建议呈现“读取记忆变量 → 意图识别 → 检索/选用 Skill → 必要信息表单 → 业务工具 → 回答检查 → 输出”；可先用已有节点和变量实现，不必把每一项都开发为新节点。轨迹复盘与候选更新放在会话结束后的异步流程，避免拖慢客服响应。新工具涉及退换货、退款等操作时，应由表单确认并验证真实业务结果。

## 对照 Hermes 闭环逐项判断

目标闭环为：

```text
采集轨迹 → 归因与评价 → 提炼候选更新 → 隔离验证 → 版本化发布 → 监控、回滚与继续学习
```

### 1. 采集轨迹：部分具备

当前系统已经保存用户问题、最终回答、会话和用户标识、工作流节点详情、耗时、知识库检索候选、模型标识、Token、费用和反馈；还有部分工具调用、表单确认信息。`workflow_manage.py` 的运行详情包含节点和上游节点标识，`tools.py` 中也有 ToolRecord 输入/输出记录，不能说完全没有工具轨迹。

`apps/evaluation/events.py` 会在聊天记录保存时生成 `EvaluationEvent`，线上质量页可以统计响应耗时、Token、点赞/点踩、无检索候选、引用可评估比例、工具调用次数等指标。

不足是没有统一的不可变 Trace/Span 模型和跨节点、工具、模型的完整关联，工具输入/输出、重试和异常恢复没有全部标准化保存。这里需要运行依据和可观测信息，不需要收集模型隐藏思维链。尤其要注意 `events.py` 中若干字段只是推断或代理值：

- `application_version` 是保存事件时查到的最新发布版本，标记为 `version_inferred`，不是执行时绑定的精确版本。
- `final_contexts` 由检索段落是否出现在提示内容中推断；`citation_ids` 为空，不能直接当作真实回答引用链。
- `prompt_snapshot`、`retrieval_snapshot` 取应用顶层配置，不保证覆盖工作流每个节点的实际参数和提示词。
- 工具次数按部分外层工具节点计数，可能遗漏 AI 节点内部多次工具调用；`human_handoff` 尚为空，任务成功依赖额外标注或业务回传。

因此目前更接近“日志 + 节点详情 + 部分证据事件”，还不是完整、可复现的训练轨迹。

结论：可以作为闭环的数据入口，但需要补充轨迹标准和脱敏策略。

### 2. 归因与评价：部分具备

已有评测集和批量评测运行、检索命中率/召回率/MRR/综合分、可选 Judge 模型、样本抽取、人工标注、规则评估、Badcase、原因分类、改进建议、线上质量指标和反馈。评测任务也已有基线报告比较、回归阈值和通过状态，不是完全没有对照能力。

这些能力可以回答“哪批问题得分低”“哪些回答慢”“哪些回答被点踩”，但还不能完整回答是检索召回错误、提示词错误、模型错误还是业务数据缺失导致失败，也不能准确判断某个节点或工具对失败的因果贡献。

已有 Badcase 原因类别包括 `data/retrieval/generation/prompt/model/permission/user/other`，但点踩、无候选、超过 10 秒等规则给出的只是归因建议，需要证据和人工复核。Judge 的引用相关性评分基于检索上下文，不等于已验证实际引用链接。线上“解决率”主要是点赞且未标为转人工的代理统计，“一轮解决率”也没有核验真实业务完成。

实验模块已有配置和稳定哈希分组函数，但没有证据表明普通聊天自动按分组路由到不同工作流版本；不能把它算作已经完成的线上灰度发布。结论：质量评价和对照基础已存在，业务真值、精确版本绑定和因果归因仍需补强。

### 3. 提炼候选更新：目前没有完整能力

已有的长期记忆提取只能从对话中提炼用户画像文本；它不会生成候选 Skill、候选工作流节点、候选系统提示词 Patch 或候选知识库修订。Skills 目前是人工创建和人工绑定，评测结果也不会自动把多条 Badcase 聚合成候选更新。

这是与所读材料描述的闭环差距最大的地方之一：除了“有 Skill 文件”，还要能在执行后判断经验是否值得沉淀，并生成可审核的 Skill 创建或更新候选。当前系统还没有这一步。

### 4. 隔离验证：目前没有专门闭环

当前评测任务虽然记录了 `run.config["application_version"]`，但 `_chat()` 没有将该版本传入运行时，而是走 `debug=False` 的普通发布版聊天链路；因此不能保证测试的是所选版本。任务直接遍历可变的 `run.dataset.cases`，也没有冻结每次运行的题目和参考答案。

基线对比报告和回归阈值可以复用，缺的是候选配置对象、精确版本锁定、数据快照和隔离运行环境，以及把质量、延迟、成本和安全检查联动审批的门禁。当前评测使用普通聊天、用户身份和真实工具，存在日志/记忆污染及工具副作用的可能；已有工具沙箱也不等于候选工作流隔离。

### 5. 版本化发布：工作流有基础，记忆和 Skill 没有

应用发布时会创建 `ApplicationVersion`，保存工作流快照和发布信息，这可以支撑工作流配置的版本化。

但目前没有长期记忆修订历史、自动进化所需的 Skill 内容版本/Diff 和候选审批状态。工作流保存的 Skill/工具 ID 仍引用可变资源；评测 `knowledge_version` 只是应用版本 ID，`model_version` 也是模型记录 ID，并不代表知识内容或模型权重被冻结。因此已有的是应用配置快照，还不是 Prompt、Skill、知识内容、工具、模型和评测集全部绑定的不可变能力版本。

### 6. 监控、回滚与继续学习：监控有，回滚和继续学习不足

已有线上质量指标、测评记录、样本审核、Badcase、实验配置/分组、对话日志和用户点赞/点踩。工作流发布历史也已有“恢复版本”操作，可将历史工作流放回编辑画布，再保存、发布；不能说完全没有恢复旧配置的能力。

不足是没有针对 Prompt/Skill 版本的自动告警门槛，没有候选 Skill 的自动撤销和负迁移检测，评测结果不会自动反哺 Prompt、Skill 或模型训练，也没有轨迹压缩、训练数据导出、GRPO/RL 训练和模型部署回流。

结论：已经有“看板式监控”，还没有 Hermes 式“监控驱动更新和回滚”。

## 哪些能做，哪些很费劲

### 近期可做，主要复用现有能力

1. 启用灯具助手长期记忆，但默认只记录用户偏好、背景和明确约定。
2. 配置少量经过人工审核的客服 Skills，例如“售后信息收集”“订单查询前置检查”“真人客服话术规范”。
3. 复用已有 Badcase 分类，补充人工复核和证据备注，先区分知识缺失、检索错误、生成错误和业务能力缺失。
4. 复用基线比较报告做人工迭代；在版本锁定完成前，明确记录实际发布配置，不能宣称已可靠对比两个指定历史版本。
5. 在画布和运行详情中标明记忆是否启用、Skills 是否绑定，以及业务分支只是话术还是真实执行。

### 中等到较大成本，需要补齐产品和运行底座

1. 候选改进中心：从低分题、点踩、Badcase 和人工备注中聚合候选 Prompt、Skill 或知识库更新。
2. 候选版本隔离运行：先锁定工作流、提示词、Skill/工具内容和评测集快照，再实现候选执行入口、工具模拟及数据副作用隔离。这涉及运行时改造，不能只新增评测页面。
3. 审批门禁：候选版本必须满足总体得分、关键分类、延迟、成本和安全拒答阈值后才能发布。
4. Skill 版本和 Diff：保存 Skill 的来源轨迹、创建者、修改原因、测试集结果和回滚版本。
5. 受控发布与回滚：复用历史工作流恢复能力，补齐发布指针、实验路由、监控门禁及关联资源版本；配置回滚不会撤销已发生的退款等业务操作。
6. 完整轨迹：统一节点、工具和模型调用标识，记录输入/输出摘要、失败重试、精确版本、脱敏结果和证据来源；不能把这部分当作简单加日志。

### 很费劲，不能承诺短期完成

1. 无人审核下，自动决定创建或更新 Skill 并稳定提高质量；生成候选原型相对容易，证明有效且没有负迁移才是难点。
2. 完整的 Skill 内容审查、权限分级、来源可信度和提示注入防御。已有路径检查、沙箱和 Deep Agents Skills 加载可以复用，不需要把它们全部从零实现。
3. 多版本并发更新、跨会话一致性，以及适配不同供应商的缓存优化；缓存收益取决于请求结构和模型服务，不能承诺固定成本或通用单消息方案。
4. 完整的 Trace → 压缩 → RL/GRPO → 评估 → 模型部署回流。
5. 从真实用户数据直接自动训练模型，并同时保证隐私和能力不退化。
6. 自动因果归因，即准确判断某个节点或工具是失败根因，而不是只做相关性统计。

这些部分不是增加一个数据库表或一段 Prompt 就能完成，需要新的数据模型、异步任务、安全策略、评测门禁、模型训练资源和运维流程。

**当前系统不能直接完成的边界**：只接供应商推理 API 时，不能在 MaxKB 内直接对其闭源模型权重做 GRPO/RL；如需权重训练，应使用可训练模型并接外部训练、评估和部署平台。没有订单、库存、工单或坐席系统接口，就不能靠记忆或 Skill 获得真实业务执行能力。不存在“装一个 Skill 即可保证持续变强”的可靠捷径，但受控的提示词、Skill 和检索策略迭代可以在现有架构上逐步实现。

## 建议的落地路线

### 阶段一：先确认基线并用好已有能力

- 先保存当前发布配置和基线题目；若确有跨会话偏好需求，再为灯具助手启用长期记忆，同时配置引用、身份、查看和删除机制；
- 在 AI Chat 节点配置少量人工审核过的 Skills；
- 保留当前真人客服 Prompt，不让记忆或 Skill 覆盖“不能编造、不能说知识库”的基本规则；
- 在评测集增加“记忆是否误用”“是否提及内部实现”“是否正确转人工”等检查题。

这一阶段的验收应包括：同一用户的新会话能按配置复用偏好，不同用户不串记忆；运行详情能说明选用了哪个 Skill；订单、库存和转人工未接系统时不能虚构执行成功。真人客服口吻首先依赖话术策略、足够的业务知识和工具结果，不需要为了改善口吻强行开启长期记忆。

### 阶段二：建立可追溯的改进闭环

```text
对话轨迹 → 质量指标/人工标注 → Badcase 聚合 → 候选 Prompt 或 Skill Patch
→ 固定测试集验证 → 人工审批 → 发布工作流版本 → 线上监控
```

建议先交付“版本锁定与题目快照 → 隔离评测 → 候选中心 → 审批发布与回滚”，再接候选自动生成，避免先生成大量无法可靠验证的改动。候选需保存来源轨迹、归因证据、变更 Diff、影响范围和评测结果；初期每次只改变一种策略，便于判断变化来源。

这一阶段不要求 Agent 完全自主。候选更新由系统生成，发布仍由人审批。验收要求是：相同冻结输入能重放；候选不影响线上记忆和业务数据；退化候选被门禁拦截；发布后能找到对应报告，并恢复上一套关联配置。

### 阶段三：再引入受控的自动进化

只有阶段二的评测、审批、版本和回滚稳定后，才适合增加自动审查 Agent：只能从已脱敏轨迹和已确认 Badcase 生成候选，只能写入隔离空间，必须通过固定测试集和安全测试，默认不直接发布，并保留来源、Diff、评测结果和回滚点。

这比直接照搬 Hermes 的“Agent 自动写 Skill”更适合企业客服场景，因为客服系统最怕把一次性错误、用户恶意提示或不完整业务信息沉淀成长期规则。

## 最终判断

当前 MaxKB 已经具备自进化所需的若干“零件”：长期记忆、Skills、工作流编排、应用版本、轨迹记录、评测、线上质量和 Badcase。但这些零件目前是分开的：记忆不会自动变成 Skill，Skill 不会根据轨迹自动更新，评测不会自动产生候选版本，版本不会自动灰度、回滚和继续学习，轨迹还不能直接进入可靠的 RL 训练管线。

因此对当前系统最准确的评价是：**具备“可配置记忆和可评测工作流”，不具备完整的 Hermes 式自进化。** 最现实的方向是先做“候选生成 + 隔离评测 + 人工审批 + 版本回滚”的受控闭环，再逐步增加 Skill 自动提炼，而不是一开始就做完全自主的模型权重进化。

## 对“中等到较大成本”部分的进一步规划

前面列出的中等到较大成本，不能按“补几个页面、加几张表”来排期。它们同时涉及产品对象、工作流运行时、评测可信度、资源版本和线上发布控制。建议把目标定义为**受控改进平台**：系统可以从证据中提出候选，能够在固定输入和隔离资源中验证候选，经过审批后发布，并且能定位、撤回和复盘；暂不把目标定义为无人值守的自动学习。

### 一、先明确要新增的产品对象

产品侧先建立以下对象和状态，不要直接把 Badcase 改写成线上 Prompt：

| 对象 | 需要保存的内容 | 推荐状态 |
|---|---|---|
| 改进候选 | 来源轨迹/Badcase、问题归因、拟修改对象、Diff、影响范围、生成方式 | 草稿、待验证、验证失败、待审批、已批准、已拒绝、已发布、已撤回 |
| 能力版本 | 工作流快照、Prompt、Skill 内容版本、工具授权、模型、知识和评测集快照的引用 | 草稿、候选、已验证、已发布、已归档 |
| 评测运行 | 题目快照、版本清单、运行模式、隔离策略、指标、门禁结果 | 排队、运行中、通过、失败、取消 |
| 发布批次 | 发布的能力版本、灰度比例、开始/结束时间、操作者、回滚点 | 待发布、灰度、全量、已回滚 |

候选必须保留“为什么产生、改了什么、由谁批准、用什么题目验证、对哪些指标产生影响”。同一个候选可以反复验证，但每次验证都要生成不可变的运行记录。这样才能回答“这次改动是否真的解决了这个 Badcase”，也能避免多人编辑时覆盖彼此的结论。

### 二、产品侧的分阶段交付

#### 阶段 A：可追溯基线（约 2–4 周，取决于现有接口和迁移窗口）

目标是先让每次评测和发布都能被准确复盘，不追求自动生成候选。

1. 为测试集和评测运行创建不可变快照；运行记录保存题目、参考答案、检索目标和标签的快照，而不是继续读取会变化的 `dataset.cases`。
2. 在执行入口传入明确的 `application_version`，让评测真正运行指定版本；结果中同时列出工作流、Prompt、Skill/工具、模型、知识库和评测集版本。
3. 在评测记录中增加“证据链”展示：输入、命中的段落、实际引用、节点输出摘要、工具调用结果、最终回答和错误；对推断值明确标记“推断”，不把它画成已验证事实。
4. 为人工标注增加归因证据和置信度，区分知识缺失、检索失败、生成不当、业务接口缺失和用户输入不足。

阶段 A 的验收条件：同一快照可以重复运行并找到同一组输入；运行详情可以准确说明版本和资源；修改线上测试集或发布新版本不会改变历史报告；至少能从一条 Badcase 回溯到对应轨迹和节点详情。

#### 阶段 B：候选中心与人工审批（约 4–8 周）

目标是把复盘结果变成可审核的改进工作，不自动上线。

1. 新增候选中心：按应用、版本、问题类别、来源和状态筛选，展示影响样本、拟修改 Diff、风险说明和验证报告。
2. 第一版只支持人工创建或模板化生成三类候选：Prompt Patch、人工编写的客服 Skill 新版本、知识库维护任务。候选生成模型可以给建议，但不能直接写入生产资源。
3. 复用已有基线比较和回归报告，增加硬门禁：总体分数、关键业务分类、拒答安全、延迟、成本、工具错误率均不得超过设定阈值；任何关键类别退化都需要人工豁免并留下原因。
4. 审批时强制选择影响范围和回滚点；审批通过后只生成“待发布能力版本”，仍由发布操作进入线上。

阶段 B 的验收条件：候选可以被验证、驳回、再次修改和审计；验证失败不能进入发布；线上版本和候选版本互不污染；一次发布能关联完整的 Diff、评测报告和审批人。

#### 阶段 C：受控发布、灰度和回滚（约 4–8 周）

目标是让“已验证”真正成为可控的线上变更。

1. 建立发布指针，明确当前生产版本，而不是在请求时隐式取最新发布记录。
2. 把工作流、Prompt、Skill/工具授权、模型配置、知识快照和评测集快照绑定到同一个能力版本；资源内容需要内容哈希或不可变版本号。
3. 接入实验分组和稳定路由，先支持按应用、用户或会话灰度；记录每次请求实际命中的版本，不能只记录配置的目标版本。
4. 监控质量、延迟、成本、错误率、转人工和安全事件。达到门槛时自动停止灰度并告警；自动回滚只切换配置指针，不声称可以撤销已经发生的退款、写库或外部业务操作。
5. 提供一键恢复上一能力版本和手工冻结发布的操作，同时保留回滚原因。

阶段 C 的验收条件：灰度和全量请求都能按版本统计；指定版本可以停止接收新流量；回滚后新请求进入旧版本；外部副作用有幂等键、确认和补偿流程，不能靠配置回滚消除。

### 三、运行底座的拆分方式

产品页面依赖下面四个运行底座，建议按顺序建设。

#### 1. 精确轨迹与证据层

把现有 ChatRecord、节点详情、ToolRecord 和 EvaluationEvent 统一成带 `trace_id`、`span_id`、父子关系、开始/结束时间、状态、资源版本和脱敏摘要的事件。记录模型输入输出摘要、检索候选、实际引用、工具参数校验结果、重试和异常；不要收集模型隐藏思维链。需要增加数据保留、敏感字段脱敏和访问权限策略。

#### 2. 快照与隔离执行层

评测开始时冻结题目、工作流、Prompt、Skill 文件、工具清单、模型配置和知识检索所需的版本。候选运行使用独立的会话用户、记忆空间和临时数据；真实退款、库存修改、发消息等工具默认采用模拟器或只读模式，工具结果由固定夹具提供。评测运行结束后清理临时状态，禁止把候选产生的记忆或 Skill 文件写回生产。

#### 3. 评测门禁与异步任务层

把评测、Judge、分组统计和回归比较放在异步任务中，支持取消、重试、超时和幂等。门禁配置应版本化，至少覆盖质量、关键分类、延迟、成本、安全和工具副作用。评测报告要区分“没有数据”“运行失败”和“指标为零”，避免把缺失证据当成低分。

#### 4. 资源版本、发布和观测层

工作流的 `ApplicationVersion` 可以作为起点，但还要为 Skill、Prompt、工具授权、模型参数和知识快照补充版本或内容哈希，并在发布时做完整性校验。线上事件记录实际版本，监控按版本和实验组切分。发布、灰度、回滚和候选审批都要有操作审计。

### 四、依赖关系和建议排期

推荐顺序是：

```text
版本/题目快照 + 精确轨迹
        ↓
隔离评测与可重复回归
        ↓
候选中心 + 审批门禁
        ↓
资源版本绑定 + 灰度发布
        ↓
按证据生成候选的自动审查 Agent
```

前两步没有完成时，不应开放“自动更新 Skill”按钮；否则候选无法证明是在哪个版本、哪组题目和哪份知识上得到的，也无法安全回滚。若按一个熟悉 MaxKB、能同时改后端和前端的工程小组估算，阶段 A 通常是数周级，阶段 B 和 C 各是数周到数月级；真实时间取决于迁移、工具模拟、权限审计和上线窗口，不能承诺短期一次完成。若只有一名开发者，应把每个阶段再拆成多个迭代，并先交付只读追踪和人工流程。

### 五、明确成本和不承诺范围

- **可以规划但要排期**：候选中心、版本/题目快照、隔离评测、人工审批、灰度指标和配置回滚。这些是工程建设，难点在跨模块一致性和数据迁移。
- **需要外部系统配合**：订单、库存、售后、工单、坐席转接和真实业务成功率。没有接口和测试环境，只能展示话术或模拟结果。
- **需要专项安全工作**：Skill 内容审核、权限分级、提示注入防御、敏感信息脱敏、租户隔离和并发写入冲突处理。已有沙箱和路径检查只能复用为基础，不能替代安全评审。
- **不承诺短期实现**：无人审核的稳定自我改写、跨模型通用缓存收益、自动因果归因、从供应商闭源 API 直接做 RL/GRPO，以及从真实用户数据直接训练并保证不退化。这些需要长期数据、可训练模型或外部训练平台、专门评测和运维能力。

每个阶段都应设置“停止条件”：如果版本绑定仍不准确、隔离运行仍会污染真实数据、关键安全题退化，宁可停留在人工候选和只读报告，也不要把自动发布作为默认能力。这样可以把高成本目标拆成可验收的产品增量，同时保留向自进化闭环演进的路径。

## 本轮“近期可做”落地记录

本轮先落地可以复用现有工作流、记忆和评测能力的部分，范围如下：

- 灯具知识问答助手已开启长期记忆，使用默认 LLM，按 10 轮对话触发提取；工作流开始节点提供 `memory` 变量，客服回答节点仅在相关且可信时引用它。长期记忆仍应只保存用户偏好、背景和明确约定，不保存敏感凭据。
- 已创建并绑定“灯具真人客服回复规范” Skill，内容约束客服口吻、事实边界、内部实现隐藏和订单/售后信息不足时的处理方式。它是人工审核的运行技能，不是自动学习出来的技能。
- 已发布新的工作流版本，客服回答节点包含 Skill 绑定和长期记忆引用；原有“不能编造业务结果、不能说知识库/文档”的规则继续保留。
- 评测运行快照和线上轨迹增加了能力摘要：长期记忆是否启用、是否绑定 Skill、是否配置订单/售后/库存/转人工分支，以及本次是否出现业务工具调用记录。这里的“工具调用记录”不等于订单已完成、库存已确认或已经成功转人工。
- 评测结果抽屉和样本审核展开区会展示上述摘要，便于区分“配置了能力”“本轮使用了记忆/Skill”和“有真实业务结果”。

本轮没有把已有的 MySQL 数据库 Skill 误挂到灯具客服，也没有虚构订单、库存或售后接口。后续若要验证长期记忆是否真正改善回答，需要用同一用户的跨会话偏好题和不同用户隔离题进行人工评测；若要验证业务成功率，仍必须接入可返回真实结果的订单、库存、售后或坐席系统。

## 阶段 A“可追溯基线”开发记录

阶段 A 已完成第一版实现，当前范围覆盖“题目冻结、版本锁定、资源摘要、运行证据和人工归因字段”。

### 已实现

1. **评测题目快照**：创建评测运行时，将测试集名称、内容版本和题目数组深拷贝写入 `Run.config.dataset_snapshot`。历史运行不再依赖后续变化的 `Dataset.cases`；空题目数组也会保持为空，不会回退读取当前数据。
2. **指定发布版本执行**：评测启动时保存 `application_version`，执行时通过 `application_version_id` 传入开会话和聊天接口。简单应用和工作流都按该 `ApplicationVersion` 加载；会话缓存的序列化、还原和重建都保存版本 ID。
3. **资源快照摘要**：运行配置保存独立计算的工作流 SHA-256 和 Prompt SHA-256、默认及节点模型 ID、知识库 ID、工具 ID、Skill ID 和 Skill 名称/版本/文件 ID/文件哈希。移动节点只改变工作流摘要，不改变 Prompt 摘要。它用于追溯运行配置；知识库正文和 Skill 文件内容的不可变版本仍属于后续资源版本建设。
4. **逐题证据**：评测结果保存检索上下文和工作流节点详情，结果抽屉可以展开查看检索证据、节点证据、回答和参考答案。节点详情展示运行摘要，不收集模型隐藏思维链。
5. **人工归因补充**：样本标注增加归因置信度（高/中/低）和归因证据备注，并在样本展开区展示。原有分类和答案标注保持兼容。
6. **原快照重跑**：测评记录增加“按原快照重跑”，创建新运行并保存 `replay_of`，保留原题目、参考答案、检索目标、标签和应用版本。缺少快照或原发布版本已删除时拒绝重跑；重跑重新记录当前资源摘要，原报告不变。测试集名称、版本和报告导出同样读取冻结值。
7. **Badcase 回溯**：样本审核和 Badcase 均增加“查看证据”抽屉，展示轨迹 ID、执行/推断版本、输入回答、检索段落、人工归因和节点详情。历史样本从原会话补读节点时明确标记来源；缺失证据不伪装成已验证引用。新节点证据剔除显式 reasoning/thinking 字段，新增“业务接口缺失”归因分类。

## 阶段 B 开发记录：候选中心与人工审批

本轮完成阶段 B 的第一版人工闭环。应用评测页新增“候选中心”，候选按状态、类型、问题类别、来源和基线版本筛选；详情包含关联 Badcase、冻结的轨迹证据、Prompt/Skill Diff、风险说明、逐题前后回答、门禁报告和操作审计。

- 候选类型固定为 Prompt Patch、人工编写的客服 Skill 版本和知识库维护任务。模板只填入待人工确认的草稿；保存和生成只写入候选表，不改工作流、Skill、知识库、会话或长期记忆。
- 创建候选时冻结应用版本、测试集题目、逐题检索证据、已绑定 Skill 的 `SKILL.md` 内容和哈希，以及模型配置指纹。候选验证使用同一批题目和证据做离线成对回答与 Judge，不执行完整工作流、工具、脚本或长期记忆；知识维护任务把拟维护正文作为明确标注的检索夹具。
- 总体分数、安全、延迟、成本、工具错误率和缺少指标都是硬门禁。安全按单题最低值检查；成本需要模型返回 Token，否则报告标记缺失并禁止批准。业务类别退化只能逐项填写豁免原因，不能用放宽阈值跳过。
- 验证任务使用修订号和快照哈希，重复投递只允许一个任务运行；编辑会递增修订并使旧报告失效；可取消排队或运行中的验证。审批会锁定应用和候选，必须填写影响范围、回滚的线上 `ApplicationVersion` 和类别豁免理由。
- 审批产物是独立的 `CapabilityVersion`，状态为 `pending_release`，清晰关联候选、Diff、完整报告、审批人和回滚版本；审批不会创建或切换 `ApplicationVersion`，也没有自动发布入口。撤回会标记该待发布产物，不触碰线上资源。
