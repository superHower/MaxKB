### 当前代码已覆盖的范围与验收边界

1. **评测基础链路已有实现**：数据集、运行、基线比较、规则指标、可选 Judge、结果快照和历史报告。
2. **工作流 Agent 的质量闭环已经具备雏形**：节点证据、检索跳过/无命中诊断、原配置展示、候选修改、Badcase 关联；候选修改仍需在应用编排中应用、发布并重新评测后才能标记解决。
3. **检索配置和兜底正在按节点暴露**：知识库、Top-K/检索参数、分支去向、无结果回复和转人工位置可以被查看和维护。
4. **目前不能宣称已完成**模型选型基准、多轮评测、多 Agent 协作、安全合规套件和完整可观测告警；这些属于后续阶段。

### 建设优先级

- **第一优先级**：把现有 10 条 Badcase 的候选修改在应用编排中应用，发布新版本，重新跑回归，再根据结果关闭 Badcase。
- **第二优先级**：补齐轨迹/工具调用/多轮数据结构，先让每个失败都能定位到具体节点、分支或检索参数。
- **第三优先级**：建设模型横评、Prompt/RAG 变体实验和灰度统计；
- **第四优先级**：验证门禁、Token/成本硬限制按要求后置。安全合规、多 Agent 协作和完整告警体系。

因此，`spec3.md` 中列出的内容并非全部已经存在：基础评测、RAG、Judge、候选闭环、灰度和线上指标已有可用实现；模型选型、多轮、多 Agent、安全、完整轨迹评测和成熟监控仍需按上面的顺序建设。

### 第一、第二优先级落地情况（2026-10-25）

**第一优先级：Badcase 改进闭环**（质量中心 → 改进上线 → 改进方案详情）

1. **应用到编排**：把审核过的修改写入应用编排草稿，不发布。写入前核对节点仍是候选记录的原配置；被他人改过则拒绝写入，提示手动合并。关联 Badcase 转为“处理中”。
2. **发布新版本**：仍在应用编排中人工发布。系统不代发布。
3. **回归验证**：要求最新发布版本已包含此修改。题目为基线测评的冻结题目，加上来源 Badcase 的问题（同一问题去重；参考答案取人工标注的 gold_answer）。Judge 配置沿用基线。
4. **自动关闭 Badcase**：同时满足以下两条才关闭，并写入解决说明：
   - 基线题目无回退；
   - 该问题判定为“已修复”：无节点失败、分支/工具断言通过、Judge 分 ≥ 0.6。

   没有 Judge 分或参考答案时标为“需人工确认”，不自动关闭。

现有 10 条 Badcase 需要在界面上按以上四步操作，涉及 3 个改进方案。代码已经就绪，实际数据还没有操作。

**第二优先级：轨迹、工具调用、多轮数据结构**

- **统一轨迹 `trace`**：离线测评每题和线上事件都会记录。内容是按执行顺序排列的节点步骤，包括：
  - 节点 ID、类型、状态、错误、耗时；
  - 分支决策（意图或条件分支名）；
  - 工具调用（工具 ID、名称、参数、结果）；
  - 检索参数（知识库、top_n、similarity、search_mode、命中数）；
  - 多轮轮次。
- **测试集新增可选字段**：
  - `expected_tools`：期望按顺序调用的工具，`[]` 表示不应调用工具。生成 `tool_call_accuracy`、`tool_order_correct`、`tool_error_rate`。
  - `expected_branch`：期望进入的分支。生成 `branch_correct`。
  - `history`：同一会话中先发送的前序问题。按真实多轮执行，只对最后一轮评分。
- **问题诊断**：展示执行路径，标出失败节点和定位节点。新增“分支走错”“工具顺序错”两条诊断。检索类诊断附带实际检索参数。
- **适用范围**：只对功能上线后的新测评和新对话生效。旧记录没有 `trace`，诊断照旧。
